## 並行する全チャットの必須作業手順

1. **毎回、執筆前に** GitHubの `coord/reading-450-registry` から `docs/reading-450-ledger.json` と `data/reading/entrance/manifest.json` を再取得する。過去のチャット回答や別PRの登録数を使わない。
2. 候補IDが `accepted_ids` と `reservations[].id` のどちらにもないことを確認。分野別の `next_suggested_id` は候補にすぎず、予約の成功ではない。
3. **IDの予約を先に行う。** GitHubの `fetch_file` で取得した**最新のblob SHA**を使い、同じ共通ブランチ上の **同じ台帳ファイル** に `reservations` を追加して `update_file` する。予約の各項目: `id`, `owner`（作業チャット/担当ラベル）, `work_branch`, `reserved_at`, `status:"reserved"`。
4. 更新がSHA競合などで失敗した場合は、**そのIDでの執筆・保存を行わず**台帳を読み直して別の空きIDを選ぶ。古いSHAを使い回して更新を繰り返さない。GitHubの同一ファイル更新時の整合性チェックを予約ロックとして使う。
5. **執筆用ブランチは最新の共通ブランチから作る。** 予約済みIDの教材ファイルは `create_file` だけで作成する。既存の `L##-###.json` の内容を別稿で置換しない。元の題材と英文を照合し、意味的な重複もできる限り防ぐ。
6. 完成したら本文と訳文、語彙・日本語語義・類義語・英語定義、10問の4択＋根拠、文法4・論理展開4・言い換え4・穴埋め4の**内容と形式**を確認。保存後に `python scripts/reading_450_guard.py --ids L02-012,L03-012` などでチェックする（指定IDはその回の制作IDに変更）。このスクリプトは**ローカル検査**であり、遠隔のID予約処理は代行しない。
7. 検査済みファイルを共通開発ブランチへ取り込み、`manifest.json` の `sets` を追加し、**台帳の `accepted_ids`・総数・分野別数・`reservations` を整合させる**。このときも最新SHAを取得し、競合すれば再読してやり直す。2チャットが別々のブランチで総数を増やしたと報告するのは禁止。
8. **Draft PRを作成する場合は、共通開発ブランチの最新版を基準とする。** 差分に既存IDの文章の置換がないか、他のPRとIDが重複しないか確認する。mainや本番へは統合しない。
9. 完了時には「**共通開発ブランチで実際に登録済み**」の本数と「**各チャットの執筆ブランチだけにある未統合分**」を分けて報告する。重複IDや未統合作品を登録数に足さない。

## 実行可能な検査

```powershell
python scripts/reading_450_guard.py
python scripts/reading_450_guard.py --ids L02-011,L04-011,L07-011
```

標準ライブラリのみ使用。台帳とmanifestの一致、ID・ファイル名の整合、**同じ英文全文の重複**、指定教材の語数・レベル・全文和訳・語彙本文出現・4択・参照先を検査します。昔からある28本には読解問題が8問のものもあるため、**厳密な10問チェックは今回指定した新稿のみに適用**します。

ただしスクリプトは、**内容が似た別稿の意味的重複や正答の曖昧さを自動的に完全検出するものではありません**。開発時の検査だけで本番公開可能と宣言しないこと。

## 使い方の重要な制約

- GitHubの台帳ファイルを読む**だけ**では重複を予防できません。両チャットとも同一ファイルへの予約更新が成功している必要があります。
- 他チャットがこのルールに従っていない場合、そのチャットの作業は依然として衝突する可能性があります。作業開始時にこの文書と共有台帳の場所を伝えてください。
- 元のPR #55と#56のように同じIDでも本文が別なら、**別IDで回収してから登録**します。
- 既存教材の公開状態を勝手に変更しないでください。今回の回収原稿も`status:"draft"`のままです。
